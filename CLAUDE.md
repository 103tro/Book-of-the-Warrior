# Книга воїна — проєктна довідка

Цей файл — передача проєкту. Якщо ти читаєш це на початку нової сесії (користувач написав щось на кшталт «продовжуємо роботу над Книгою воїна») — тут усе, що треба знати, щоб одразу працювати правильно, без повторних питань і без втрати якості.

**Користувач — проджект-менеджер, не технічний спеціаліст.** Пояснюй технічні рішення простою мовою, не завалюй його жаргоном. Він диктує задачі часто голосом (текст буває не зовсім точний/плутаний) — якщо щось незрозуміло або може стосуватися реальних людей/фактів, перепитай, а не вгадуй.

## Що це за проєкт

Сайт-книга для **103-ї окремої бригади територіальної оборони імені митрополита Андрея Шептицького** (ЗСУ). Це не маркетинговий сайт — це свого роду меморіальна/довідкова «книга» про бригаду: історія, командування, батальйони, герої, духовні засади, дозвілля особового складу, медіа. Її читають військовослужбовці (часто зі смартфона, часто з поганим інтернетом) і, ймовірно, їхні родини.

**Звідси два жорсткі пріоритети:**
1. **Точність щодо реальних людей.** Імена, звання, фотографії, дати служби — усе про справжніх, живих (або загиблих) військовослужбовців. Переплутати чиєсь фото з іменем, вигадати факт, неправильно підписати — неприпустима помилка, не просто технічний баг. Якщо є найменша двозначність — питай, не вгадуй.
2. **Швидкість на мобільному.** Сайт раніше важив 7.4 МБ (все було вшито base64 в один HTML) і довго вантажився на слабкому зв'язку — це вже виправили (виніс усі фото/шрифти в окремі файли, зараз `index.html` ~325 КБ). Будь-яка нова робота має зберігати цей принцип: не роздувати вагу сторінки, стискати фото розумно, не ламати lazy-loading.

## Головні правила роботи (не ламай ці)

- **Не вигадуй і не вгадуй факти, імена, дати.** Якщо користувач дав документ/фото — бери з нього дослівно. Якщо чогось бракує (наприклад, фото людини немає) — скажи про це прямо, не підставляй заглушку як факт.
- **Перш ніж публікувати зміну на сайті — покажи чернетку, якщо йдеться про новий текст чи підбір фото.** Користувач кілька разів просив «кинь сюди, подивимось» перед тим, як щось остаточно лягало на сайт. Для дрібних правок (виправити помилку, замінити вже узгоджений формат) показувати чернетку не обов'язково — дій і звітуй по факту.
- **Перевіряй у браузері перед пушем.** Локальний сервер + Playwright-скріншот — мінімум: зображення завантажились (`naturalWidth > 0`), немає `pageerror` в консолі, слайдер/лайтбокс клікається. Для верстки — перевіряй і на desktop, і на мобільному viewport (390×844), бо сайт переважно читають з телефону.
- **Кожна зміна йде окремим PR** через фоновий `Agent` (деталі нижче) — не накопичуй кілька незв'язаних правок в один коміт/PR, якщо користувач явно не просив об'єднати.
- **Перевикористовуй наявні UI-компоненти** (слайдер, лайтбокс, згортання тексту, таблиця) — не вигадуй новий JS-патерн, якщо старий можна переналаштувати зміною розмітки/даних. Деталі — нижче.
- **CI в репозиторії немає.** Це означає, що ніхто не зловить твою помилку автоматично — відповідальність за коректність лежить повністю на перевірці перед пушем.
- **Після кожного великого блоку правок** (кілька пов'язаних ітерацій/виправлень поспіль) — онови розділ «Уроки з практики» нижче конкретними пастками, які реально зустрілись, щоб наступна сесія (чи ти сам пізніше) не наступала на ті самі граблі.

## Як ми працюємо з користувачем

- Повідомлення часто **голосові/диктовані** — трапляються неточності, обірвані фрази, повтори. Якщо щось не сходиться з контекстом (наприклад, плутанина в назві теки чи імені) — краще перепитати одним коротким реченням, ніж піти не туди і потім переробляти.
- Фотографії та документи зазвичай лежать у **Google Drive** користувача (`g:\My Drive\...` — це змонтований диск на його Windows-машині; для нас доступ через MCP-конектор Google Drive за назвою теки/файлу). **Завжди перевіряй, що знайдена тека — саме та, яку мав на увазі користувач**, звіряй вміст, дати створення файлів, перш ніж братися за обробку — траплялося, що він називав не ту теку.
- Коли користувач каже «я підготував зображення» або дає нове посилання — **довіряй файлам з ТІЄЇ теки як вже готовим**, не перекроюй їх по-своєму, навіть якщо вже зробив щось своє раніше. Якщо не певен, що це саме те фото/той самий кадр — звір вручну (переглянь обидва).
- Коли щось на сайті виглядає зламаним/дивним з боку користувача — спочатку перевір сам (локально, через GitHub API), а не вір на слово і не вір власному припущенню, що ти «напевно помилився» — часом причина в кеші браузера чи затримці деплою GitHub Pages, а не в реальному багу.

## Середовище виконання (технічні пастки)

- У контейнері є **два Python**: `python3` (3.11 — PIL/Pillow тут БИТИЙ, `ImportError: cannot import name '_imaging'`) і `python3.13` (повноцінний, робочий Pillow/numpy/scipy). **Завжди використовуй `python3.13` для роботи із зображеннями.** Якщо модулів немає — `pip install pillow numpy scipy playwright` (без `--user`).
- Playwright: `executable_path='/opt/pw-browsers/chromium'` обов'язково в `launch()`. Ніколи не `playwright install`.
- Локальна перевірка: `python3 -m http.server 8765` в корені репо, потім Playwright на `http://localhost:8765/index.html`. На старті сторінки — intro-overlay: закривається кліком по `#introOverlay` (force=True), пауза ~1.1с на анімацію, потім `#introOpenBtn`.
- Мобільна навігація схована за гамбургером `#navBurger` — на вузькому viewport перед кліком по вкладці відкрий бургер-меню.
- Bash-heredoc ламається на апострофах/лапках в українському тексті (напр. «в'язнів»). Для Python зі складним текстом — пиши файл через `Write`-tool, не `<< 'EOF'` heredoc.
- `pkill -f "http.server ..."` часто видає exit code 144 — це нормально, не помилка.

## Редагування index.html

- Файл великий (~325 КБ) і майже без переносів рядків — **звичайний `Edit`-tool часто не спрацьовує** (рядок не унікальний/задовгий). Для точкових правок (особливо в `subnavData`, довгих JS-об'єктах, вставка/перенесення HTML-блоку) — пиши Python-скрипт, який читає файл, робить `str.replace`/`re.sub` з `assert` на унікальність, пише назад.
- `subnavData` — JS-об'єкт `{tabId: htmlString}` на одному рядку, живить дропдаун «Зміст». Редагуй через `json.loads`/`json.dumps` (валідний JSON), не руками.
- Для «Батальйони» є окремий `battalionSubnavData` (`{battalionGroupId: htmlString}`) — див. нижче.
- Нумерація `id="collapse-N"` наскрізна по всьому файлу (не по вкладці). Перевіряй поточний максимум перед додаванням нового: `grep -o 'id="collapse-[0-9]*"' index.html`.

## Повторювані HTML-патерни (копіюй, не вигадуй наново)

- **Картка з текстом, що згортається**: `<div class="collapsible-body" id="collapse-N">...</div><button class="read-more-btn" data-target="collapse-N">...` — JS сам ховає кнопку, якщо `scrollHeight <= 170`, тож можна безпечно обгортати навіть короткий текст.
- **Банер-фото зверху картки**: `<div class="photo-slots n1"><img class="photo-slot-img" style="aspect-ratio:X/Y;" src="..." alt="..."></div>` — `aspect-ratio` обов'язково під РЕАЛЬНІ пропорції файлу. Два фото поруч — `photo-slots n2`.
- **Слайдер фото** (Дозвілля, командири батальйону, управління): `.leisure-gallery[data-gallery]` → `.leisure-slide` (перший — `active`) → `img.leisure-photo`, плюс `.leisure-nav.prev/.next` і сусідній `.leisure-dots`. JS generic (`querySelectorAll('.leisure-gallery')`) — нових слайдерів можна додавати скільки завгодно без правок JS.
  - Квадратний варіант (портрети): клас `square` на `.leisure-gallery` (`aspect-ratio:1/1`).
  - Підпис на фото (ім'я/посада/період): `<div class="person-caption"><span class="person-name">...</span><span class="person-role">...</span><span class="person-period">...</span></div>` всередині `.leisure-slide` поруч з `<img>`.
- **Лайтбокс-зум** спрацьовує на `img.photo-slot-img`, `img.roster-photo-sm`, `img.org-shevron-sm`, `img.leisure-photo` — нове фото, яке має зумитись, познач одним з цих класів.
- **Список нагород**: `<ul class="awards-list"><li><span class="awards-date">...</span><span>...</span></li>...`.
- **Таблиця даних**: `<table class="results-table">`, `overflow-x:auto` wrapper для мобільного скролу.
- **Шеврон у «Структурі бригади» → посилання на сторінку підрозділу**: якщо для підрозділу зі списку org-list (`Бригада → Структура бригади`) уже є власна сторінка (напр. у «Батальйони»), обгорни його `<img>` + `<span class="org-name-sm">` у `<a class="org-link-battalion" href="#ID-розділу-підрозділу">` (клас `display:contents`, тож flex-розкладка `<li>` не ламається). Лайтбокс-обробник уже має `if (e.target.closest('.org-list a')) return;`, тож зум не конфліктує з переходом. `applyHash()` сам активує потрібну `.battalion-group`, якщо ціль посилання — усередині неї. Нічого більше міняти не треба — просто додавай такий `<a>` для кожного нового підрозділу, що отримав власний опис.
- **YouTube-відео**: facade-патерн `.video-embed.lite-yt` з `data-src`, `<img class="lite-yt-thumb">` (fallback maxresdefault→hqdefault + onload-перевірка на generic 120×90 плейсхолдер), `<button class="lite-yt-play">` — ніколи не вставляй сирий `<iframe>` напряму.

## Навігація: вкладка з кількома підрозділами (патерн «Батальйони»)

Якщо в одній вкладці верхнього рівня з'являється кілька логічно окремих «розділів» (як батальйони) — НЕ клади їх у один плаский `subnavData`, список «Зміст» стане кашею. Патерн:
1. Кожен розділ — свій `<div class="battalion-group" id="bgroup-XXX">` (усередині звичні `<section class="card">`), перемикається класом `.active`.
2. Пікер-перемикач над контентом — кнопка `.subnav-toggle`/`.subnav-dropdown` (ті самі класи що й «Зміст», інші id), пункти `.battalion-picker-item[data-battalion][data-label]`.
3. `battalionSubnavData[groupId]` — свій набір пунктів «Зміст» на кожен розділ; `updateSubnavFor` сам підхоплює активний розділ.
4. Новий розділ пізніше = новий `.battalion-group` блок + новий пункт пікера + новий запис у `battalionSubnavData`. Жодних правок JS не потрібно.

## Джерела контенту (Google Drive)

- Конектор `mcp__Google_Drive__*`. Великі зображення (>10 МБ base64-результат) — `download_file_content` падає з «exceeds maximum tokens», результат зберігається у файл в `/root/.claude/projects/.../tool-results/*.txt` як JSON `{content: base64, title, ...}`. Декодуй через `python3.13`: `json.load()` → `base64.b64decode(data['content'])` → записати у файл у scratchpad, потім `Read`-tool щоб візуально перевірити.
- Реальний порядок зображень, вбудованих у .docx, перевіряється не вгадуванням по підписах-коментарях у тексті, а прямим розбором .docx: `download_file_content` без `exportMimeType` дає сирий base64 ZIP (OOXML) → розпакувати, `word/media/` містить файли в порядку вставки; АБО конвертований `.htm`-експорт (якщо лежить поряд у Drive) містить `<img src="...">` у точному порядку документа — надійніше за ручне співставлення підписів.

## Уроки з практики (поповнюється після кожного великого блоку роботи)

Після кожної великої ітерації/блоку правок додавай сюди конкретні пастки й уроки — не загальні фрази, а те, що реально збило з пантелику або зламалось, щоб наступного разу не наступати на ті самі граблі.

**З доопрацювання батальйону «2 ББпС «Хижий Птах»» (кілька раундів правок після першого запуску):**

- **Довіряй явним підписам-коментарям у тексті документа** («Зображення image-002.png» біля абзацу) **більше, ніж «фізичному» порядку вбудованих медіа-файлів, які сам видобув з .docx.** Один раз сталось навпаки: поклався на порядок файлів у великому оригінальному docx замість підписів у скороченому тексті — і розставив фото бойового шляху неправильно (довелось переробляти). Підписи в тексті — це явний намір автора документа, саме їм і довіряй, а не «перевіряй» їх видобуванням медіа іншим шляхом.
- **`.symbol-figure` (ряд, лише зображення) ≠ `.symbol-cell` (колонка, зображення + підпис).** Легко переплутати: якщо під зображенням потрібен підпис — завжди `.symbol-cell`, інакше підпис ляже збоку, а не знизу (саме так і сталось один раз, виправляли окремим фіксом).
- **Формат імені військовослужбовця, що усталився після кількох ітерацій:** `Ім'я Прізвище [«Позивний»]`, без по-батькові; звання і/або посада — окремим текстом, із званням у кінці через кому (напр. «Савич Анатолій, підполковник» чи «Начальник штабу — заступник командира батальйону, капітан»). Відповідає стилю, який уже був у «Бригада → Командування». Якщо користувач просить прибрати звання, перепитай — ми вже один раз прибирали, потім повертали назад, бо він звірився з наявним на сайті зразком.
- **Квадратні фото-слайдери (`.leisure-gallery.square`)** на десктопі обмежені `max-width:320px` (медіа-запит `min-width:641px`) — стандарт, щоб портретні фото не розтягувались на всю ширину картки. Застосовуй його одразу для будь-якого нового квадратного слайдера, не чекай окремого запиту.
- **Список нагород має 2 готові варіанти стилю**: `.awards-date` (дата зліва, як у «Бригада → Нагороди») і `.awards-count` (кружечок-число справа, як у батальйонних нагородах). Обирай залежно від даних: дата події чи кількість нагороджених.
- **Факти (цифри нагород, назви населених пунктів тощо) звіряй із першоджерелом щоразу, коли є найменший сумнів** — навіть якщо щось уже написано на сайті. Якщо точного числа/факту користувач не пам'ятає і просить тимчасове значення — постав explicit placeholder і прямо скажи, що це тимчасово, щоб не загубилось як «вже готовий факт».

**З фото командира Андросюка (спроба виправити «боком» фото), нової цитати Шептицького та UI-правок навігації слайдера/deep-linking батальйонів:**

- **AI-генерація зображень (Gemini) потребує оплаченого білінгу** — на безкоштовному API-ключі image-моделі (`gemini-2.5-flash-image`, `gemini-3-pro-image` тощо) мають квоту 0, хоча текстові запити тим самим ключем проходять нормально (можна перевірити `models?key=...` і дешевим текстовим запитом). Перш ніж обіцяти користувачу «розвернути»/згенерувати фото через AI — спочатку перевір квоту, а не витрачай час на повний image-запит, який все одно впаде з 429.
- **Розворот пози людини на фото неможливо коректно виправити звичайною обробкою зображень** (crop/padding тугішим кадром) — це міняє лише рамку, а не саму позу, і користувач це одразу помітить («ну ліпше не стало»). Якщо AI недоступний (немає бюджету) і кращого фото нема — чесно скажи про межі можливого й попроси нове фото, а не видавай перекадрування за «виправлення».
- **Перевірка деплою через `mcp__github__get_file_contents` на великий файл**: якщо результат зберігається окремим файлом, сам збережений файл може починатись з короткої обгортки `<persisted-output>…Full output saved to: <інший шлях>` — реальний повний вміст лежить за ЦИМ другим шляхом, а не в тому, що дав виклик інструмента. Пошук рядка в першому (неправильному) файлі дає хибний «не знайдено» — завжди перевіряй, чи файл не є такою обгорткою, перш ніж робити висновок.
- **`.leisure-nav` (стрілки слайдера) має єдиний стандартний стиль по всьому сайту**: без темного кола-підложки, лише стрілка з `filter:drop-shadow(...)` для контрасту на будь-якому фото; на десктопі (`min-width:641px`) прихована (`opacity:0`) і з'являється при `:hover` на `.leisure-gallery`; на мобільному — завжди видима (бо немає hover, саме тому кола там НЕ треба — досить тіні). Новий слайдер — одразу копіюй цей стиль, не питай окремо.
- **Deep-linking на батальйон довершено**: вибір пункту в `.battalion-picker-item` тепер викликає `history.pushState(null,'','#'+gid)` (раніше оновлював лише вміст, URL лишався старим). Сама логіка «відкрити потрібний таб+групу за хешем» (`applyHash`) вже була генеричною й працювала для будь-якого `#bgroup-XXX`, бракувало тільки цього одного виклику в обробнику пікера — для майбутніх батальйонів нічого додатково робити не треба.
- **У заголовках карток усередині вкладки з підрозділами не повторюй слово, яке й так зрозуміле з контексту** («Результативність батальйону» → «Результативність», «Командири батальйону» → «Командири» в межах вкладки «Батальйони»), **але лишай уточнення, якщо воно несе інший сенс, а не дублює контекст** (напр. «Нагороди воїнів батальйону» — тут «батальйону» уточнює ЧИЇ нагороди (особового складу, не підрозділу як такого), тому лишається).

## Загальний робочий цикл на кожну правку

1. Прочитати задачу, за потреби уточнити через `AskUserQuestion` (особливо щодо реальних людей/імен/ідентичності на фото).
2. Обробити зображення (`python3.13`), скопіювати в `images/`.
3. Внести правки в `index.html` (CSS/HTML/`subnavData` за потреби).
4. `python3 -m http.server 8765`, Playwright-перевірка: зображення завантажились, немає `pageerror`, слайдер/лайтбокс клікається, скріншоти desktop + мобільний (390×844).
5. `pkill` сервер, `git add` конкретні файли (перевір `git status`, не `-A` бездумно), осмислений commit message, `git push -u origin claude/warrior-book-code-changes-hsxnej`.
6. Делегувати створення+мердж PR фоновому `Agent` з повним контекстом.
7. Коли агент повертає результат — коротко підтвердити користувачу номер PR і що задеплоєно.
