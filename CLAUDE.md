# Книга воїна — 103 окрема бригада ТрО

Сайт-книга для 103-ї окремої бригади територіальної оборони імені митрополита Андрея Шептицького. Розраховано переважно на перегляд зі смартфона, часто з повільним інтернетом — швидкість завантаження і компактність зображень мають значення.

## Структура файлів

- `index.html` — весь сайт одним файлом (~325 КБ після рефакторингу, раніше було 7.4 МБ з inline base64). Мінімум переносів рядків — великі блоки (CSS, `subnavData`, секції вкладок) часто лежать в одному довгому рядку.
- `images/*.webp` — усі зображення сайту, WebP, ~100+ файлів.
- `fonts/*.ttf` — 4 нарізки шрифту «UAF Sans» (400/500/600/700).
- Немає build-кроку, немає package.json — чистий статичний HTML/CSS/JS.

## Середовище виконання (важливо)

- У хмарному контейнері є **два Python**: `python3` (3.11, з довідки — PIL/Pillow тут БИТИЙ, `ImportError: cannot import name '_imaging'`) і `python3.13` (повноцінний, з робочим Pillow/numpy/scipy). **Завжди використовуй `python3.13` для будь-якої роботи із зображеннями** (PIL, numpy, scipy). Якщо `python3.13 -c "import PIL"` падає — `pip install pillow numpy scipy playwright` (без `--user`, це одноразовий контейнер).
- Playwright (`python3.13 -m playwright` або просто `from playwright.sync_api import sync_playwright`) з Chromium за адресою `/opt/pw-browsers/chromium` — **завжди передавай `executable_path='/opt/pw-browsers/chromium'`**, не викликай `playwright install`.
- Для локальної перевірки: `python3 -m http.server 8765` у корені репо (фоном), потім Playwright на `http://localhost:8765/index.html`. На старті сторінки завжди є intro-overlay — закривається кліком по `#introOverlay` (force=True) з паузою ~1.1с (анімація), потім `#introOpenBtn`.
- Мобільна навігація схована за гамбургером `#navBurger` — на вузькому viewport клік по вкладці спершу вимагає відкрити бургер-меню.
- Bash-heredoc ламається на апострофах/лапках в українському тексті (напр. «в'язнів»). Для Python-скриптів з текстом, що містить апострофи/лапки — пиши файл через `Write`-tool, не через `<< 'EOF'` heredoc, або екрануй апостроф як `chr(39)`.
- `pkill -f "http.server ..."` часто рапортує exit code 144 — це очікувано/нешкідливо (сигнал від вбивства фонового процесу), не помилка.

## Редагування index.html

- Через величезний розмір і мінімум переносів рядків — **звичайний `Edit`-tool часто не спрацьовує** (рядок не унікальний / занадто довгий для контексту). Для точкових правок (особливо в `subnavData`, довгих JS-об'єктах, і коли треба вставити/перемістити HTML-блок) — пиши невеликий Python-скрипт (через `Bash` з inline heredoc БЕЗ апострофів, або через `Write` + запуск), який читає файл, робить `str.replace`/`re.sub`, пише назад. Перевіряй `assert` на унікальність/наявність патерну перед заміною.
- `subnavData` — JS-об'єкт `{tabId: htmlString}` на одному рядку, що живить дропдаун «Зміст» кожної вкладки. Редагуй через `json.loads`/`json.dumps` (він валідний JSON) — не руками.
- Для вкладки «Батальйони» є окремий `battalionSubnavData` (`{battalionGroupId: htmlString}`) — `updateSubnavFor('tab-battalions')` резолвить його через активний `.battalion-group`, а не через `subnavData` напряму.
- Нумерація `id="collapse-N"` — наскрізна по всьому файлу, не по вкладці. Поточний максимум: **52** (перевіряй `grep -o 'id="collapse-[0-9]*"'` перед додаванням нового).

## Повторювані HTML-патерни (копіюй, не вигадуй наново)

- **Картка з текстом, що згортається**: `<div class="collapsible-body" id="collapse-N">...</div><button class="read-more-btn" data-target="collapse-N">...` — JS сам ховає кнопку, якщо `scrollHeight <= 170`, тож можна безпечно обгортати навіть короткий текст.
- **Банер-фото зверху картки**: `<div class="photo-slots n1"><img class="photo-slot-img" style="aspect-ratio:X/Y;" src="..." alt="..."></div>` — `aspect-ratio` обов'язково вказувати під РЕАЛЬНІ пропорції файлу (крадуть лейаут інакше). Два фото поруч — `photo-slots n2`.
- **Слайдер фото** (`Дозвілля`, командири батальйону, управління): `.leisure-gallery[data-gallery]` → `.leisure-slide` (перший — `active`) → `img.leisure-photo`, плюс `.leisure-nav.prev/.next` і сусідній `.leisure-dots`. JS повністю generic (`querySelectorAll('.leisure-gallery')`), нових слайдерів можна додавати скільки завгодно без правок JS.
  - Квадратний варіант (портрети): додай клас `square` до `.leisure-gallery` (`class="leisure-gallery square"`) — фіксований `aspect-ratio:1/1`.
  - Підпис на фото (ім'я/посада/період): вкладай `<div class="person-caption"><span class="person-name">...</span><span class="person-role">...</span><span class="person-period">...</span></div>` всередину `.leisure-slide` поруч з `<img>` — відображається оверлеєм знизу фото, перемикається разом зі слайдом автоматично.
- **Лайтбокс-зум** спрацьовує на клік по `img.photo-slot-img`, `img.roster-photo-sm`, `img.org-shevron-sm`, `img.leisure-photo` — новий тип фото, яке має зумитись, додавай одним з цих класів, а не новим.
- **Список нагород**: `<ul class="awards-list"><li><span class="awards-date">...</span><span>...</span></li>...` (ліва колонка — дата/число, права — текст).
- **Таблиця даних**: `<table class="results-table">` зі стандартним `<thead>/<tbody>`, `overflow-x:auto` wrapper для мобільного скролу.
- **YouTube-відео**: facade-патерн `.video-embed.lite-yt` з `data-src`, `<img class="lite-yt-thumb">` (ланцюжок fallback maxresdefault→hqdefault, плюс onload-перевірка на generic 120×90 плейсхолдер) і `<button class="lite-yt-play">` — не вставляй сирий `<iframe>` напряму, це білий текст на синьому.

## Навігація: нові вкладки з кількома підрозділами (патерн «Батальйони»)

Якщо в одній вкладці верхнього рівня з'являється кілька логічно окремих «розділів» (як батальйони в «Батальйонах»), НЕ клади їх у один плаский `subnavData` — список «Зміст» стане кашею. Патерн:
1. Кожен розділ — свій `<div class="battalion-group" id="bgroup-XXX">` (усередині — звичні `<section class="card">`), перемикається класом `.active` (`display:flex` в CSS).
2. Пікер-перемикач над контентом — кнопка `.subnav-toggle`/`.subnav-dropdown` (ті самі класи, що й «Зміст», інші id), пункти `.battalion-picker-item[data-battalion][data-label]`.
3. `battalionSubnavData[groupId]` — свій набір пунктів «Зміст» на кожен розділ; `updateSubnavFor` сам підхоплює активний розділ.
4. Додати новий розділ пізніше — просто новий `.battalion-group` блок + новий пункт пікера + новий запис у `battalionSubnavData`. **Жодних правок JS не потрібно.**

## Специфікації зображень

Усе — WebP, `method=6`. Якість залежить від типу:

| Тип | Розмір | Якість | Приклад |
|---|---|---|---|
| Банер картки (верх секції) | 1500×500 (3:1) | 85 | `battalion-2bbs-banner.webp` |
| Фото в «Дозвіллі» (слайдер) | 1200×900 (4:3) **або** 950×633 (3:2) — консистентно в межах ОДНІЄЇ галереї | 85–88 | `leisure-proyav-N.webp` |
| Портрет командира/роти (квадратний слайдер з підписом) | 500×500 (1:1) | 90 | `battalion-2bbs-cmd-*.webp` |
| Портрет «Герої» (на всю картку) | 500×708 (~A4) | — | `hero*.webp` |
| Шеврон/символіка (прозорий фон, де потрібно) | під оригінальні пропорції файлу | 82–90 | `symbol-*.webp`, `collapse-4-N.webp` |
| Ростер-мініатюра (круглий кут, маленька) | 500×500 вихідний файл, CSS показує як 130×130 | 90 | `collapse-3-N.webp` |

Кадрування квадратних портретів — **top-biased crop** (трохи зсунути вниз від верху кадру), щоб не впиралось точно в маківку, залишаючи природний «повітря» зверху.

**Коли користувач каже «я підготував зображення» або дає нове посилання на Google Drive-теку — довіряй файлам з ТІЄЇ теки, не перекроюй їх сам, навіть якщо попередньо вже обробив щось своє.** Якщо вже щось зробив з інших джерел (напр. з docx) — явно звір назви файлів/розміри, щоб переконатись що береш саме те, що підготував користувач, а не повторно генероване.

Прозорість фону для нашивок/шевронів: НЕ використовуй глобальний поріг яскравості (background ≈ eyes/деталі теж світлі → ріже важливі елементи). Натомість — flood-fill від рамки зображення (`scipy.ndimage.label` + перевірка, які компоненти дотикаються країв), щоб прибирати лише фон, зв'язаний з краєм, а не будь-який світлий піксель.

## Джерела контенту (Google Drive)

- Є конектор `mcp__Google_Drive__*`. Великі зображення (>10 МБ base64-результат) — `download_file_content` падає з «exceeds maximum tokens», результат зберігається у файл в `/root/.claude/projects/.../tool-results/*.txt` як JSON `{content: base64, title, ...}`. Декодуй через `python3.13`: `json.load()` → `base64.b64decode(data['content'])` → записати в `.webp`/`.png`/`.jpg` файл у scratchpad, потім `Read`-tool щоб візуально перевірити.
- **Перш ніж писати код по наданих фото/документах — перевір, що тека/файл справді той, що мав на увазі користувач.** Траплялось, що користувач диктував неточну назву теки чи плутав, яка саме тека містить «готові» фото — краще перепитати/звірити вміст (список файлів, дати створення), ніж здогадуватись.
- Реальний порядок зображень, вбудованих у .docx, можна звірити не вгадуванням по підписах-коментарях у тексті, а прямим розбором .docx: `download_file_content` без `exportMimeType` дає сирий base64 ZIP (OOXML) → розпакувати, `word/media/` містить файли в порядку вставки, АБО конвертований `.htm`-експорт (якщо є в Drive поряд) містить `<img src="...">` у точному порядку документа — надійніше за намагання співставити підписи-коментарі вручну.

## Загальний робочий цикл на кожну правку

1. Прочитати задачу, за потреби уточнити через `AskUserQuestion` (особливо коли йдеться про реальних людей/імена/ідентичність на фото — помилка тут неприпустима).
2. Обробити зображення (`python3.13`), скопіювати в `images/`.
3. Внести правки в `index.html` (CSS/HTML/`subnavData` за потреби).
4. Підняти `python3 -m http.server 8765`, прогнати Playwright-перевірку: завантаження зображень (`naturalWidth`), відсутність `pageerror`, скріншоти ключових станів (desktop + мобільний viewport 390×844), перевірка лайтбоксу/слайдера де релевантно.
5. `pkill` сервер, `git add` конкретні файли (не `-A` бездумно — перевір `git status`), осмислений commit message, `git push -u origin claude/warrior-book-code-changes-hsxnej`.
6. Делегувати створення+мердж PR фоновому `Agent` з повним контекстом (власник, гілка, що змінилось, вимога звичайного merge commit).
7. Коли агент повертає результат — коротко підтвердити користувачу номер PR і що задеплоєно.

## Чого НЕ робити

- Не вгадувати, яке фото кому належить (прізвище/особа), якщо є найменша двозначність — питати.
- Не форсити один аспект-ratio на всі фото в секції, якщо джерельні кадри суттєво відрізняються за орієнтацією (портрет vs альбомна) — або підібрати індивідуальний `aspect-ratio` під кожне, або явно уточнити стандарт.
- Не вигадувати новий UI-патерн (нову кнопку/дропдаун/слайдер з нуля), якщо існуючий (`subnav-toggle`, `leisure-gallery`, `awards-list` тощо) можна перевикористати зміною лише даних.
- Не редагувати `index.html` наосліп через `sed`/`Edit` без попереднього читання точного фрагмента — файл надто щільний, ризик зламати сусідній JS/CSS високий.
